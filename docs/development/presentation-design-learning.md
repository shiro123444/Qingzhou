# PPT 设计能力接入与 Mac 视觉学习

本轮将 `/Users/july/Project/ppt-master` 的 Style 方法和 Layout 原型接入清舟，并用同一份三页中文验收内容检查生成结果。上游项目保持原样；部署路径由 `CORDIS_PPT_MASTER_ROOT` 指定。

## 新任务的视觉规则

`deck-visual-system.ts` 新建的视觉合同使用 schemaVersion 3。它记录共同字体、画幅、参考色板和可读性建议，页面作者拥有完整画幅、标题层级、留白及可选页码。服务端只登记设计合同标识，不再重新画通用页眉、标题和页脚，不再逐节点重写字体或将颜色映射到固定色板。

已保存的版本 1/2 合同仍使用旧渲染方式，避免打开旧任务时改变产物。分镜阶段也区分新旧合同，新合同不再被改写为“母版已绘制、只排正文”。Style 的方法规则会送入分镜，Layout 槽位作为几何参考，不要求绘制可见容器。

原生流程图增加可选的颜色、字体和圆角参数；原生表格增加可选的字体、表头文字色和行底色。没有这些字段时保留原行为。事实、文字和关系仍由结构化渲染器处理。

## Style 与 Layout 的来源

`ppt-master-library.ts` 只读取部署者指定目录中索引注册的 Style 规格和 Layout SVG 原型：

- 本次解析了 14 套 Style 与 86 个布局原型，来自 7 套 Layout 工作区。
- Style 保存方法规则及适用关键词；Layout 提取原生槽位的比例坐标、页面角色和画幅，不复制原型里的示例数据和占位文字。
- 每条能力记录工作区种类、ID 和源内容 SHA-256；源或适配规则更新时生成新能力 ID，旧记录退出自动选择并保留历史文件。
- 初次导入只是设计参考，不等于通过了试作或得到用户接受。使用记录、自动质量证据和用户反馈继续各自保存。
- 检索纳入当前提示词；选择器排除不同画幅的原型。默认生产装配在账号首次使用时自动准备库，仍遵守账号资源隔离。

没有两类索引的旧转换器安装可以继续工作；只有一类索引的残缺安装会明确报错。

## 本机真实模板学习

使用上游 `template_preview_pptx.py` 将 `presentation_core` 工作区导出为真实 PPTX，工具验证了 20 页、1 个母版、20 个版式与 65 个完整占位框。随后通过清舟的 `TemplateVisualLearning` 学习真实渲染页面。

首轮实际观察第 1、14、20 页，即封面、流程和清单原型，产出 2 条视觉能力。第二轮已分批观察完 `presentation_core` 全部 20 页，当前覆盖为 20/20，累计 5 条视觉能力。86 个原型仍属于结构解析，不能描述为 86 页全部完成视觉观察。

Mac 模板渲染默认使用 `/Applications/LibreOffice.app/Contents/MacOS/soffice`；其他位置可用 `PRESENTATION_OFFICE_COMMAND` 配置。本机字体设置为 `CORDIS_PRESENTATION_FONT_FAMILY="Hiragino Sans GB, Arial"`，避免依赖 Windows 微软雅黑。

上游转换器会把 Hiragino Sans GB 规范化为 Microsoft YaHei，导致 Mac 上真实导出与浏览器预览使用不同字体。本机显式设置 `CORDIS_PRESENTATION_EXPORT_FONT_MAP='{"Microsoft YaHei":"Hiragino Sans GB"}'`，转换后仅恢复指定字体别名，保留字号、位置和其他字体；没有配置则保留转换器行为。讲稿只存口头讲解内容，结构化图表源保留在 `metadata.contentBlocks`，读取旧讲稿时剥离历史内部源附录，防止每次修订重复追加。

本机模型网关实际提供 `deepseek-v4.1-flash` 与 `glm-5.3-flash`；已登记在模型目录中的其他名称不代表网关可调用。红色图片实测确认 GLM 能读取图像，故设置 `CORDIS_PRESENTATION_VISION_MODEL=glm-5.3-flash` 用于后续视觉复核；文本生成继续使用账号原有模型，账号密钥和连接不变。


真实请求暴露并修复了两个接入问题：候选名额会被相似布局挤满，导致需要的原生类型缺席；视觉刷新会把绑定了同一模板版本的工作区原型误当旧视觉能力下架。现在原型导入与视觉观察各自维护生命周期，视觉刷新不会下架工作区原型。保留了中间验证记录，未把这些未完成试作计入最终稳定性结果。

稳定性请求固定原始提示词和相同三页事实，不指定能力 ID，不追加逐页修饰指令。三份任务共享请求指纹，生成、实际应用记录、表格换行、原生文字与讲稿、PPTX 导出分别验证。私有请求和结果位于 `.data/ppt-design-comparison/stability-*`；最终结果只以完成态文件和真实预览为准。三份样本是当前内容与风格组合的初步验证，不构成对所有题材和模板的可靠性承诺。

复核合同也同步修改：早期故事板中的卡片、强调条和底板属于候选构图，不能在原生编译已采用学习布局后反过来要求补回。复核输入对有实际编译回执的原生对象改用批准内容、结构化节点关系和实际几何；图片、公式及未编译页面仍保留原有要求。严重内容缺失、遮挡和关系错误继续阻止发布，新合同使用独立复核缓存版本，旧意见不会被伪装成已经解决。

真实上游导出校验另发现两个兼容性问题：背景角色需要稳定 ID；可编辑文字组不能依赖缩放变换。编译器现在生成背景 ID，流程图将缩放落实为真实坐标和字号；恢复旧草稿时也会重新渲染原生块并补齐标识。表格末行同样参与宽度平衡，避免虽然没有单字尾行、仍留下很短词片段的贪心断行。

本轮最终针对性回归为 20 个文件、225 项通过，完整类型检查通过。连接中断时只保留草稿和工程排版验证文件，不能绕过在线复核修改任务完成状态；工程样本检查报告在 `pending-layout-verification.json`，与完成态稳定性结果分开记录。

生成与自动修复现共用实际布局编译。恢复任务时依同一账号选中的能力重新编译已有原生页，重算应用回执；若修复后超出编译支持范围则清除旧回执，避免把已被改写的风格继续算作实际应用。流程节点标签与独立正文完全重复时只保留原生节点中的可编辑文字，节点关系和其他句子不变。回归覆盖修复后重编译、连续编译不重复标签，以及无缩放变换的真实字号导出。

## 第三轮：补齐编译覆盖与阶段证据

第二轮未编译的三页有两个可复现原因：两页的标题由短标题改成了断言式标题，旧编译器按文字相等查找标题而退出；另一页把表格和侧栏文字改为纵向堆叠，重新测量后超高。现在用字体、位置和原生对象关系识别标题载体并保留完整标题，表格使用源 `table` 与右侧 `body` 槽位，流程使用源主体中心带及下方 takeaway 槽位。恢复与自动修复都会重新尝试所有支持的 v3 原生页，未编译过的页面不再被旧回执条件排除。

真实新草稿又暴露了原始文字载体并不适合直接作为正文：局部坐标会把页码误判为正文，数字步骤说明会变成松散段落，原型的说明标签会与结论重复。因此 compilerVersion 3 从已批准大纲与原生图表数据分配正文，图表已承载的事实不再重复画成散句；原型的标题、页脚载体和布局用于设计，示例标签不进入新事实。没有批准内容的旧调用继续保留原文字路径；分组的平移、缩放与继承字号按页面坐标读取。
