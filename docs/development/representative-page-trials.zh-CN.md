# 代表页对照试跑（设计与执行器）

## 目标和边界

在现有 Cordis 原子操作、能力记忆、真实渲染和视觉检查上增加有证据的对照实验。
同一份输入保留原页，最多试跑两个布局候选，比较后推荐一个方案；推荐不等于替换作品。
第一步只实现评价契约、保守选择与独立记录，不接入默认生成、不调用模型、不自动提升能力。
第二步增加可信宿主按需装配的 Cordis 试跑执行器，完成配置、候选预检、独立渲染工作区、预算与取消。第三步接入真实模型 probe、Sharp SVG 渲染和一次批量匿名评价；默认生产生成链保持原接线。

不采用 Harness² 排除 baseline 的选择池。原方案始终存在，候选失败、证据不足、质量退步、平局或用户拒绝时保留原方案。
如果原方案本身不合格，保留表示 “不采用候选”，不表示原方案通过发布验收。

## 结合 Harness² 的设计补充

本地参考版本为 `/home/shiro/harness2` 的 `1cfe254`（包版本 0.1.0）。
其核心可借鉴之处是优化执行配置：同一任务提出配置差分、真实执行、从行为对比合成配置，
再将采用的完整配置树与有证据的经验用于后续同领域任务。
代表页对照是清舟验证这条链路的首个受限实验，单次选出更好的页面不能证明配置在新任务上有效。

源码中需要区分的两种 “保留原方案”：

- `core/selection.py:selection_pool()` 仅纳入 `agg1..aggk` / `c1..ck`，明确排除参考执行。
  prompt 中存在 mixed pool 模板，不代表默认运行路径会把原始输出加入最终选择池。
- 提案 / 合成阶段的 `KEEP_BASE` 可以保留当前配置；串行模式保留的是本轮输入检查点。
  清舟仍明确把原页放入对照池，并允许最终不采用任何候选。

全链路需要以下约束；本轮实现范围和后续部分见 “小步交付”，不把底座测试描述为完整配置优化闭环：

1. **保存可复现执行配置。** 除试验记录之外，冻结原方案和每个候选的完整解析配置快照：
   能力规则 / 内容摘要、装配配方、宿主允许的规划参数、实际模型配置版本、插件版本与执行器版本。
   原始配置加显式 patch 产生候选，省略字段继承；按 schema / 白名单拒绝未知字段。
   首轮只开放布局能力差分，不能由模型更改授权、注册模块或导入任意路径。
   共享的 `conditionFingerprint` 只覆盖不变条件；每份完整执行配置另有自己的指纹，不能把待比较的布局差分混进共享指纹。
2. **分离提案、匿名评价与事后测量。** 提案器按任务需求和合法执行证据生成差分。
   评价器只接收固定资料、用户约束及匿名真实渲染，不接收 baseline 标记、能力排名或候选生成说明；
   宿主保存稳定随机排列与身份映射，在收齐评价后恢复身份，由现有保守规则选择。
   `0–4` 产品质量评价不是独立外部 judge；若增加留出任务 / 基准测量，其答案、rubric、分数和通过标签不得进入提案、合成或在线经验库。
   可读性、事实完整等用户可见要求仍可作为正常产品约束。
3. **核算实际预算。** Harness² 的 `R=4k / P=3k` 不包含选择、反思及所有重试成本。
   清舟保留已定的候选 / 渲染 / 评价上限，并逐阶段记录实际调用、重试、取消、耗时和 token / 费用。
   未执行与失败分开记录，不为满足次数恒等式继续消耗预算；seed 控制排列或任务顺序不代表模型采样确定。
4. **经验绑定配置和适用范围。** 后续经验保存采用的完整配置快照与来源证据，引用内容寻址且不可变的材料；
   索引可摘要，但摘要不能代替实际复现配置。库按账号、任务领域和实验版本隔离。
   只读取当前任务之前已确认的条目；单页改善先作为候选经验，再用整稿和其他任务验证适用范围。
   保留负面结果、失败与撤回，不承诺 “越跑一定越强”。

## 固定条件和候选隔离

1. 由可信宿主从当前账号的完成任务读取 job/version/slide，复制不可变原方案。
   第一轮由用户指定代表页，默认选页策略留到后续，不能将单页胜出描述为整稿提升。
2. 冻结来源文档及版本、完整大纲、页面内容意图、事实、讲稿、主视觉系统、原素材及生成图片。
   指纹还包含实际规划 / 观察模型及供应商配置版本（不含密钥）、插件版本、渲染器、评价器、预算及随机采样设置。
   不变条件指纹由宿主规范化后求 SHA-256，候选完整配置另外求摘要；调用者不能自行声明 “相同条件”。
3. 最多两个候选，首轮只改变 layout 能力；风格、渲染配方和素材不变，不重新生图。
   从当前账号 `CapabilityMemory.compose()` 解析能力，遵守拒绝和退休能力规则。
   检索到不代表实际使用，候选记录提议能力与实际使用能力，只有后者可进入后续能力归因。
4. 原方案和各候选使用独立的 plan/version、工作目录和产物引用；整轮锁定已装配插件的版本。
   候选不能调用原任务的 page.replace/saveJob，也不覆盖原页、用户修改或原导出。
5. 每个候选按相同条件渲染并评价。不能把原方案历史评价与新候选的新评价直接比较。
   受限宿主顺序执行，最多两次候选生成、三次页面渲染和一次批量匿名评价（最多三个页面）；第一轮不自动重试、不生图。
   宿主另设总时限、模型 token / 费用上限；失败和取消记录为未完成，不能计作质量不合格。

## 评价契约

评价结果绑定 `条件指纹 + 页面产物内容 SHA-256 + 不可变预览引用 + 评价器版本`。
同条件指纹或评价器版本不一致、缺少像素证据、分数无效时，该候选没有可比较证据。
第一步校验记录形状和绑定关系；后续可信 runner 负责实际求指纹、解析所属账号产物和检查像素，字符串本身不是核验。

硬门槛全部通过才允许推荐候选：

- facts：对照原始文档和内容意图检查事实、数字、图表含义与讲稿，不能仅检查文本是否存在。
- editability：标题、正文、事实表格保持原生可编辑，不能用整页位图冒充可编辑页面。
- assets：引用可解析且属于本账号，保留来源、许可边界和实际嵌入证据。
- render：真实渲染成功，页面几何与 SVG/PPTX 检查通过。
- visual：现有视觉检查没有 blocking/major；模型给出的 passed 不能覆盖明确缺陷。

四个质量维度统一用 0–4 级，必须分别附观察证据：可读性、信息层级、构图、主风格一致性。
0 为不可用，1 为明显缺陷，2 为基本可用，3 为清晰，4 为优秀且证据充分；是否改善由同轮逐维对比判定。
第一步不引入加权总分；候选四项均不得低于原方案，且至少一项提高一级。
这是选择规则而非模型精度承诺，同一评价器必须对三份真实渲染使用同一标尺。

选择顺序：

1. 验证整轮输入，baseline 不能缺失或被候选同名替代；候选 ID 唯一且最多两个。
2. baseline 未完成或不满足硬门槛，保留 baseline，要求补证或修复，不自动选新方案。
3. 排除条件不一致、没有完整证据、硬门槛失败和用户明确拒绝的候选。
4. 自动推荐必须对 baseline 构成严格的逐维改进。多个改进候选中，只有唯一一个逐维优于其他候选时才推荐；互有优劣或同分时保留 baseline，交给用户比较。
5. 明确用户选择可以解决视觉偏好取舍，但不能绕过硬门槛与可比较证据；明确选择 baseline 永远有效。
6. 推荐结果只包含选中 ID、原因与逐候选结论。实际替换需要后续独立的用户确认和源版本 CAS；版本变动时保留原作品并重新比较。

## 经验沉淀流程

试验记录与当前 `capsules/outcomes` 分开存储，按账号隔离，保留原方案和所有候选证据。
记录包含源 job/version/slide、条件指纹、实际使用能力、评价、用户选择及选择原因。
选择结果保存 `policyVersion: 1`；读取时核对记录摘要和确定性选择结果，策略调整必须显式演进版本，不能静默重解释历史结论。
记录 ID 由规范化内容求摘要，重复保存同一记录幂等；不同条件、产物或用户选择产生新的记录，不改写旧证据。
记录在同一目录通过临时文件和硬链接一次性发布，独立写入者不能覆盖先完成的记录；文件系统不支持硬链接时写入明确失败。
同一 trialId 的多次用户决定保留为不同记录，本阶段没有 “最新意见” 查询或自动重放。

后续分三层处理：

1. **原始证据**：成功、失败、证据不足、保留原方案都可以记录，不计作能力通过。
2. **候选经验**：从实际改动提炼 cue /lesson/evidence /confidence，引用原始记录和像素；单页结果只适用于相同任务条件。
3. **可复用经验**：用户确认后，目标整稿通过现有视觉与语义验收，再沿用 `recordOutcome` 和实际能力归因。只有此时影响已验证能力的选择；自动胜出不能伪装成 accepted。

用户撤回或改变选择时追加证据；现有能力反馈的 supersedes 语义继续负责最终作品的最新评价。
不在这条链路改写全局提示词、注册任意插件或自动写入用户个人记忆。

## Cordis 接入与小步交付

1. **本轮**：`representative-trial.ts` 提供严格 schema 和确定性选择；
   `FileCapabilityCapsuleStore.recordTrial/readTrial` 保存独立证据；
   `presentation.memory.trial.read` 通过原有 memory operations 读取账号内记录。
   写入和评价数据只供可信宿主使用，不向模型提供 “提交分数即入库” 的操作。
2. **第二步已实现**：受信任的 trial runner 经现有 Cordis 操作执行能力解析、probe/render；
   做完整配置快照与差分校验、账号产物核验、能力解析、插件租约、实际预算和取消；以真实临时目录证明候选不能改原任务。
   整轮调用 `runtime.invoke()`，不新增外围 HTTP 适配层。
3. **第三步已接线，第四步补齐文本修复后的真实胜例验收**：接入源文字 / 讲稿、可编辑性、素材引用、真实 PNG 解码和匿名视觉评价；
   保存私有身份映射、渲染与评价依据，评价计入预算。第三步真实试跑均保留原方案；第四步的受限文本修复与真实对照结果见末节。
4. **最后**：增加对比 UI、明确选择及源版本 CAS；整稿复验后接入经验提炼和现有 outcome 流程。

第一步测试覆盖：平局、指标取舍、明确改进、证据缺失、硬门槛、条件不一致、用户选择 / 拒绝、无效评分、账号隔离、重试幂等，以及试验记录不会提升能力。
不把契约测试称为真实模型、像素评价或整站验收。

## 第二步执行器契约

- `trial-configuration.ts`：请求只接受源 job/version/slide 和最多两个候选；patch 只有 `layoutCapsuleIds`，省略继承，空数组表示移除布局。严格 schema 拒绝模型、指令、插件与路径等越界字段。
- `trial-runner.ts`：`createTrialExecutionPlugin` 装配不参与自主工具发现的 `trials.probe/render`；宿主显式创建 `RepresentativeTrialRunner` 并调用 `run(request, { scope, signal })`。原任务仓库仅注入 `getJob`，素材仓库仅注入 `get`；原 `port`、workerContext 和其他服务不传给适配器。
- 原方案必须属于当前账号、已完成且版本匹配。能力通过现有 `presentation.memory.compose` 解析，拒绝 / 退休能力不能借试验重新启用；全部候选校验完成后才允许生成或渲染。
- 每轮创建账号隔离的随机目录，`request.json` 和 `configuration-N.json` 一次性写入。快照包括原业务输入和完整 plan、选中页所属素材的实际字节 / 摘要、解析后的能力完整内容、配方、模型及供应商配置摘要、采样参数、插件版本 / 工具目录、执行器 / 渲染器版本和预算。
- “完整配置” 指这个受限执行契约声明的全部输入；可信适配器必须按该快照执行。额外生产参数必须先扩展 schema，不能靠未记录的环境默认值冒充可复现。凭据、请求对象、数据库连接不进入快照；`imageGeneration` 固定为 false。
- 共享条件摘要与每个候选配置摘要分开保存。候选只替换解析后的布局能力，保留原风格和配方。适配器收到深度冻结的副本和独立 scratch 路径；原页面与输出页面的 plan/slide 身份分开，旧视觉通过标记与能力归因不迁移到试跑产物。
- 本轮阶段为原页 render → 候选 probe → 候选 render，顺序执行，无自动重试。PNG 只校验格式标记和体积后保存；完成仅表示阶段产物已保存，不表示像素视觉质量、事实或可编辑性合格。
- 数量上限在执行前校验；每次 probe 在派发前预留其 token / 费用上限，不足则不派发。成功调用按回执核算，失败 / 取消但用量未知时保守计入预留额；适配器回报超额时记录实际用量并停止后续调用。`calls` 区分阶段、候选、成功 / 失败 / 取消、回执与耗时，未派发候选保持 not-started。
- 预算是每轮的接纳上限，可信供应商适配器负责把 allowance 落到实际请求中；已发生的供应商费用不能由取消撤回，也不把预留额称为实测费用。跨轮并发容量由后续生产装配复用已有宿主限流器，本轮不另造全局队列。
- 取消 / 总时限覆盖准备和执行。即使 SDK 不响应 signal，run 也会返回取消 / 超时，迟到结果不再生成正式预览或改写终态报告。仍运行的调用仅可继续写自己的 scratch；全部调用真正结束前保留插件租约。宿主应停止接纳新 run、等待现有 run 返回，再调用 `runner.drain()` 后销毁共享 runtime；这不是任意外部 IO 的强杀或第三方代码沙箱。
- 每轮最终报告默认 `selectedId: baseline`、`originalRetained: true`，不调用原任务的 saveJob/page.replace，不写能力 outcome，不自动接受候选。第二步通过注入可信 probe/render 适配器接线；第三步另见下文。默认生产工厂尚未挂载。

## 第八步：受限配置提案器（路线图第三项）

- 匿名评价继续仅接收随机标签、实际 PNG、原文事实与统一视觉约束，不接收提案、理由、经验或候选配置。推荐仍由宿主硬门槛和差异规则产生，用户明确选择及源版本 CAS 后才创建独立新稿。
