# 微信、QQ、飞书 Agent 改造流程草案

状态：整体设计草案。调研日期：2026-09-29；调研阶段只新增文档。随后经用户授权，已实现第一批入站认证、防重放及安全转发，见 [第一阶段上线说明](./channel-ingress-security-rollout.md)。尚未注册 / 启用外部机器人或完成实网验收；原始平台事件的持久 inbox、Cordis 生命周期和流式功能仍待后续实施；租约与回调可靠性进展见下段。

已完成 P1 的入站认证子集，以及微信失败转发不推进 cursor 的局部修复。随后继续落地了 P2 的 owner-token 租约、续排队记录及 Redis 回调台账，见 [可靠性首批上线说明](./channel-runtime-reliability-rollout.md)。这些不是 P0–P5 全部完成：附件安全、完整跨平台身份绑定、完整渠道 inbox 与端到端投递恢复仍需继续。回调层 SQL inbox/outbox、独立扫描器与人工核对 API 已完成第二批代码，见 [第二批说明](./channel-delivery-outbox-rollout.md)；按用户要求暂未测试、未执行迁移。

依据：[平台接入与能力调研](./channel-agent-integration-research.md)、[已有代码风险评估](./cordis-channel-assessment.md)。

## 1. 目标与范围

目标不是让每个平台都显示相同 UI，而是让它们进入同一个受鉴权、可恢复的 Agent 执行流程。平台只负责接收、认证、媒体转换与回复呈现；模型、工具权限、任务状态和产物由清舟管理。

首轮范围：现有个人微信 iLink、QQ 官方机器人、飞书企业自建应用机器人。企业微信是独立可选渠道，不把现有 `wechat` ID 改成企业微信；公众号暂不纳入首轮交互 Agent。

智能能力按顺序开放：

1. 文本 / 图片问答、上下文连续对话；文件 / 语音能力按真实附件摄取结果开放。
2. 知识检索和只读工具；长任务受理、查询、取消、恢复。
3. PPT 等创作任务及受权限保护的文件交付。
4. 明确授权后的外部写操作，例如创建飞书文档或日程；必须可确认、可审计，不能因为 “群里有人 @” 就继承机器人所有者的全部权限。

## 2. 不重写的部分

复用既有 Chat SDK、`BotMessageRouter`、`AgentBridgeService`、`AiAgentService`、`AgentRuntimeService`、工具执行与数据库；复用已有 Provider 配置体系，不为每个平台再建密钥入口。

使用现有 `@lobechat/cordis-foundation` 原生 Context 管理生命周期，参考 `messenger/platforms/cordis`。不再造一套自定义事件内核，也不把尚未完成生产装配的通用 runtime/v1 接口强行放到所有消息前面。

现有 bot 是按 Agent / 所有者配置的；共享 Messenger 的用户账号绑定是另一种产品模型。首轮保留 bot 形态并明确授权，不能把已有三平台 Bot 注册等同于共享 Messenger 账号绑定已实现。

## 3. 目标链路

```text
平台事件 / 受认证的内部网关事件
  → 平台验签、重放检查、连接归属校验
  → InboundEnvelope（只保留已验证身份和消息引用）
  → 持久 inbox（唯一事件键）→ 尽快 ACK
  → 用户/租户/Agent 路由与权限策略
  → 会话顺序队列 + 带 fencing 的租约
  → 既有 AgentRuntime / Cordis host
      ├─ 共享 Provider 配置解析
      ├─ 受控工具 / 人工确认
      └─ 持久任务状态、产物与 RunEvent
  → ReplyPlanner（平台能力、时限、额度）
  → 持久 outbox / ReplySink
  → 平台回复、文件或有权限的清舟任务链接
```

HTTP ACK 只代表可靠收件，不代表任务完成；平台 HTTP 200 也不自动代表业务发送成功，要检查 `ret` / `errcode` 等响应字段。

## 4. 拟议共享合同

以下为设计名称，不表示仓库已经存在这些类型或表。

### InboundEnvelope

包含 `platform`、`installationId`、`tenantId`（适用时）、`externalEventId`、`externalMessageId`、`actorId`、`conversationId`、`threadId`（适用时）、`receivedAt`、正文与 `attachmentRefs`、受保护的 reply context 引用。

- 身份字段只能由可信连接或验签后的事件构造，不能让客户端传一个 `userId` 就认定身份。
- 入站唯一键至少是 `(platform, installationId, externalEventId)`；缺少稳定事件 ID 的消息需设计确定性退化键并测试。
- 微信 context token、平台凭证不进入模型提示词、日志或公开 RunEvent，单独受保护存储。
- 原始消息 / 附件设置保留周期、删除与审计策略；日志默认只记事件 / 任务引用和安全错误码，不记录完整聊天正文、临时下载地址或密钥。

### SessionKey 与授权主体

至少包含 tenant/installation/platform/channel/thread + conversationOwner。DM 加入 sender；群聊明确选择 “按成员隔离” 或 “共享群上下文”，不能由相同 thread 字符串偶然合并。

机器人所有者、实际发消息者、工具执行身份、费用承担者分别建模。公开群用户默认只读 / 低预算工具；外部写操作只对已绑定或被明确授予对应权限的主体开放。

同一用户跨微信 / QQ / 飞书共享任务和记忆必须先显式绑定账号，不通过昵称或可伪造字段合并。群记忆不能默认流入个人 DM，私人文档也不能因同属一个 Agent 就回显给群成员。

渠道调用已授权 Agent 的模型选型，而不是把所有人强制映射到同一 inbox。Provider 仍从同一用户配置体系解析；任务保存非敏感 provider/model/config revision，凭证通过用户 / 连接引用在服务端解析，避免长任务中模型悄悄切换。

### PlatformCapabilities

能力按 `平台 + 会话类型 + 应用权限/开通状态` 计算，不只保留两个布尔值。

覆盖：单聊 / 群聊 / 频道，接收媒体类型，发送媒体类型，普通编辑，原生流式，交互卡片，typing，主动通知，回复上下文 / 截止时间，消息长度与分片策略，频控与幂等支持。

- QQ：C2C 原生流式与群消息分开。
- 飞书：普通消息更新与 CardKit 卡片实体流式分开。
- 个人微信：先按最终消息 + typing；不把协议里的 `message_state` 当作流式编辑承诺。
- 权限未知时按 “不具备” 处理，不通过猜测或重复失败试探权限。

### RunEvent 与 ReplySink

复用既有 operationId / 持久任务作为执行源，新增渠道投影而非另建一套任务引擎。事件具有 operationId、eventSeq、类型（受理、进度、待确认、产物、完成、失败、取消）。只展示安全的步骤摘要，不发送模型内部推理链。

模型回复、回调、以及 Agent 主动调用的消息发送工具都应经过同一发送策略，避免最终回复走 outbox、工具却直接绕过限额 / 幂等。

outbox 使用稳定业务键，例如 `(operationId,eventSeq,destination)`；记录平台 messageId、streamId/cardId、发送状态、尝试次数和下次重试时间。序号检查禁止迟到进度覆盖完成态。

没有平台幂等 / 查询保障时，网络超时后不能承诺跨系统绝对 exactly-once。记录 `unknown_delivery`，优先核对或人工重试，不能把所有超时都当作未发送而无限重发。

## 5. 分阶段执行

### P0：接入资格与协议基线

**工作**

- 个人微信确认测试账号可扫码使用；QQ 确认主体、沙箱、服务范围、事件订阅及可用流式权限；飞书创建测试自建应用、权限与可见范围。
- 用现有 UI 和测试账号做文本、图片、文件、回复、重连的最小验证；仅开白名单，不面向公众开放。
- QQ 对照最新官方域名与旧域名兼容性；更新协议契约测试后再迁移端点，不凭旧域名仍出现就断言已经失效。
- 记录每个安装实例的 capability snapshot，采集现有 ACK 延迟、首个可见反馈、端到端 P95、失败 / 重复情况作为基线。

**验收**：每个平台有可复现接入步骤和实测记录；未获权限明确显示不可用；不将沙箱成功当成公开上线已获批准。

### P1：先补可信入站与授权

**工作**

- 区分外部 webhook 与内部长连接 / 轮询转发。优先改为进程内可信调用；跨进程必须有服务身份 HMAC、时间窗、nonce，并隔离内部入口。
- 微信关闭可伪造的无鉴权转发路径；飞书外部 webhook 使用官方验证方式；QQ 按场景区分外部 Ed25519 验签和内部网关身份，不能误伤合法 WS 转发。
- 配对 / 白名单绑定实际 sender，默认不开放高权限工具；附件下载限制大小、MIME、超时、来源与重定向，防 SSRF、压缩炸弹及恶意文件。
- 通道身份到清舟身份的映射与撤销可审计；群消息和附件只是模型输入，不能修改系统授权或工具策略。

**主要落点**：各平台 client/gateway、chat-adapter、`agent-hono`、`BotMessageRouter`。

**验收**：伪造 sender、错租户、过期签名、重复 nonce、超大请求拒绝；合法事件可接收；未授权群成员不能借机器人所有者身份执行写工具。

### P2：可靠 inbox、顺序执行与 outbox

**工作**

- 先持久化入站，再 ACK / 推进微信 cursor；保留 Chat SDK 短期去重，但不再把它当作可靠收件存储。
- 将进程内 thread guard 迁移成共享 SessionKey 协调；使用 owner token + 续租 + compare-and-delete + fencing。
- 将 QStash 与既有 callback 接上持久事件 / 投递台账；删除无签名降级发送或改走合法受信通路；非 2xx 与平台业务错误都进入可观测失败状态。
- 按平台回复窗口合并消息，429 尊重平台重试提示，永久权限错误与过期 context 不盲目重试；死信可查看、可人工重投。
- 外部有副作用工具使用业务幂等键，不能只依赖分布式锁。状态 / 租约失败时停止危险写入，仍允许用户查询已完成结果。

**主要落点**：`AgentBridgeService`、`AgentStateManager`、`HookDispatcher`、`BotCallbackService`、平台 polling/client、数据库模型和迁移。

**验收**：两实例执行慢任务、进程被杀、重复回调、乱序完成、Redis 中断、平台 429、发送超时均有明确状态；已确认的重复事件不重复执行工具；不静默丢消息。

### P3：把现有渠道连接交给 Cordis 生命周期

**工作**

- 把现有 PlatformClient/Gateway 包装为 Cordis 插件，而不是重写协议 SDK。
- 用 `ctx.effect` 管理连接、心跳、轮询、订阅、定时器和清理；按 installation 分租约，避免同账号多实例抢连接。
- 支持停止新收件 → drain / 交接在途任务 → 释放租约 → 断开连接；密钥轮换仅重启对应安装实例。
- 提供连接健康度、最后收件、重连计数与队列深度；连接存活不等于 Agent/Provider 可用，分别展示状态。

**验收**：重复启停、断网重连、密钥轮换、卸载时有在途任务，不泄漏计时器、不双消费、不让别的平台中断。

### P4：分别升级三平台体验

**飞书先行**

- 应用机器人 → CardKit 流式文本 / 进度 → 停止流式后的确认卡片 → 文件 / PPT 交付。
- 卡片更新持久化 cardId/sequence，按权限和端点限频合并更新。
- 先接一个只读文档工具，再接 “确认后创建文档 / 日程”；明确应用身份与用户 OAuth 身份，资源 ACL 独立检查。

**QQ 次之**

- C2C 增加 `stream_messages` 适配，维护 stream ID、递增 index 与结束状态；失去流式能力降级普通最终消息。
- 群聊先保留 @ 触发、合并最终回复，配额不足时不刷进度；Markdown / 富媒体 / 按钮按开通能力开启。
- 所有长任务遵守回复窗口与主动消息资格，必要时给有权限的任务链接；不能假定机器人能无限主动私信。

**个人微信稳定优先**

- 可靠长轮询、context token 生命周期和 cursor 恢复优先于炫酷展示。
- 文本、图片、文件 / 语音摄取逐类验证；typing + 必要的受理消息 + 最终结果，避免消息轰炸。
- context 无效时保留任务与产物，提示下一次用户交互查询，不能把固定 Redis TTL 当成官方可投递时限。
- 微信群、任意好友主动触达、群管理不纳入本路线承诺。若需要企业群协作，独立评估 / 增加 `wecom` 渠道。

**验收**：同一受权任务在三平台语义一致但呈现不同；平台不支持的能力明确降级；审批绑定用户、任务、动作摘要和有效期，重放不生效。

### P5：灰度上线与性能验证

- 按 platform/installation 放量：内部测试 → 小白名单 → 扩大范围；每个平台可独立回退。
- 新旧链路只能做无副作用的解析 / 投影对照，不能同时执行 Agent 或发送消息。
- 数据库变更采用先兼容读写再切流，不做一次性破坏迁移；未完成任务可继续由旧消费者完成。
- 故障演练覆盖升级中断、平台限流、模型超时、审批过期、撤销权限和发送结果不明。
- 测量同一模型 / 工具负载下的首响、完成延迟、排队时长、重试成本和恢复时间。初步工程目标：ACK P95 小于 1 秒且低于平台超时门槛；最终阈值在 P0 测量后确认，不把模型生成时间算成渠道内核提速。

**发布门禁**：安全负例通过、租户不串话、无已知静默丢件、未知投递状态可追踪、单平台回滚演练通过、性能对照无不可接受回退。

## 6. 建议拆分的实现 PR

1. 平台能力与安装状态的契约、协议 fixture 和诊断页面。
2. 内外入站边界与身份映射安全补丁。
3. 持久 inbox + 微信 cursor 事务 / 恢复。
4. 会话租约、step fencing 与工具幂等。
5. 持久 outbox、回调序号 / 终态处理、发送台账。
6. 原生 Cordis 渠道插件生命周期与按安装实例健康度。
7. 飞书卡片 / 审批及文件交付。
8. QQ 域名兼容迁移与 C2C 流式；群聊发送预算。
9. 微信 context / 媒体交付体验与长任务降级。
10. 灰度、故障演练、运行手册与基准报告。

依赖关系：2 在公开联调前；3–5 是可靠长任务前提；6 不需要等待所有业务工具做完；7–9 基于同一套能力 / 事件 / 投递合同并行，但先以飞书完成纵向样板。

## 7. 实施前需要确认的产品选择

- “微信” 最终要个人助手还是企业内部协作？建议本轮保留个人 iLink；企业微信另建渠道，不混用凭证。
- 首批用户是机器人所有者、团队成员还是公开群陌生用户？这决定绑定方式、费用预算和工具权限。
- 群上下文默认逐成员隔离还是明确共享？建议默认隔离，群共享需管理员显式选择。
- 是否需要代用户读写飞书资源？若需要，单独设计 OAuth、资源权限和撤销机制。
- 长任务无法继续平台推送时，是否接受在清舟任务页查询？建议作为三平台共同兜底，但链接仍需鉴权，不用永久公开 URL。

这些选择不阻碍研究与基础安全修复，但应在公开上线和外部写工具开放前确定。
